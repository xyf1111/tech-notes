概念 02 - 解决 Bug 的流程套路

解决 Bug 的标准化流程与方法论总结。从准备工作、自行排查到寻求帮助的完整套路。

准备工作

改 Bug 就像破案，动手搜索或修改代码前先做好以下准备。

获取更多信息

搞清 Bug 何时发生、在什么条件下触发、是否可复现：

  • 操作步骤：用户做了什么操作才导致 Bug？
  • 触发频率：每次必现还是偶发？不能复现的 Bug 无法定位
  • 关键信息：详细的报错、请求参数、响应数据

明确边界

判断 Bug 属于谁的职责范围：

  • 接口划分：通过请求参数和响应参数来划分前后端/服务间的职责
  • 排除法：先确认基础环境是否正常（如用户能否访问网站、网络是否通）

保护现场

线上程序出 Bug 时，先保留当前状态再排查：

  • 保留程序运行状态：dump 内存、下载日志
  • 不要随意修改线上环境，避免丢失关键信息

自行排查

1. 自查

直接分析程序的报错信息和错误日志。许多错误从字面就能判断原因（如 db connection timeout 是数据库连接超时）。

2. 搜索引擎

搜索技巧可以大幅提高排查效率：

技巧用法说明
屏蔽广告搜索词后加 -advertisement过滤广告内容
站内搜索site:域名 + 关键词在特定站点（如 CSDN）内搜索
关键词拆解用空格组合版本号、数据库类型等关键词避免长句干扰，更精准
限定时间 / 文件类型搜索结果筛选一年内、限定文件类型技术更新快，时效重要

可选择面向开发者的搜索引擎（如开发者搜索），仅从技术站点索引内容。

3. 询问 AI

将问题描述或报错信息直接输入 AI 工具，快速获得参考答案和解决思路。与搜索引擎配合可覆盖 90% 以上的 Bug。

4. 官方文档

冷门或较新的技术，搜索引擎可能找不到答案。直接阅读官方文档的相关章节，很多 Bug 是因为阅读文档不仔细导致的。

5. GitHub Issues

使用开源项目时，在项目仓库的 Issues 中搜索。知名项目用户多，遇到的 Bug 很可能有人已解决。也可以发起新 Issue 提问。

6. 追溯源码

业务逻辑 Bug（如支付扣款后无响应）无法在网上搜到答案，因为代码各不相同。方法：

  • 从程序入口开始用 Debug 断点调试
  • 打印变量信息跟踪执行路径
  • 点击进入方法源码查看实现逻辑

7. 对比代码改动（回归 Bug）

新功能上线后老功能失效（明明没改过老代码）时，直接复现 + 断点调试复杂代码效率很低。更快的做法：对比「写新功能前的老代码」与「现在的代码」，只分析 diff 就能定位问题。

找回改动前代码的两种方法：

  • Git 提交记录：用 IDEA / VSCode 内置 Git 可视化功能查看提交记录，双击某次提交即可对比提交前后改动。建议每个功能点单独一次提交或一个分支，改动一目了然
  • 未提交的改动：IDEA 代码文件右键 → Local History → Show History 查看本地修改历史（约 30 天内的改动都能找回，删了代码也不怕）；VSCode 需先安装 Local History 扩展

寻求帮助

自己无法解决时向他人求助。注意：别人没有义务帮你，提问质量决定回答质量。

提问技巧

提问前准备好以下信息：

  1. 问题现象：遇到什么问题？有什么表现？
  2. 触发条件：在什么情况下发生？偶发还是必现？
  3. 详细日志：完整的报错信息和错误日志
  4. 已尝试的方案：列出所有排查方法和搜索过的关键词（避免别人重复尝试）
  5. 代码展示：不要拍照或只发一半，使用代码分享工具粘贴完整代码

可阅读《提问的智慧》（https://github.com/tvvocold/How-To-Ask-Questions-The-Smart-Way）学习如何提出高质量问题，参见 提问的智慧。

提问途径

途径说明
CSDN国内平台，适合初学者
Stack Overflow国际平台，更活跃、解答人数更多
GitHub Issues开源项目官方提问渠道
官方联系方式所用类库/服务的文档维护者
技术交流群编程交流小组抱团取暖

最后手段：重启

以上方法都解决不了时，试一试重启：重启大法好，Bug 逃不了；重启还不行，就卸载重装。
