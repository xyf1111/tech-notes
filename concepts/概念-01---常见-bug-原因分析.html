概念 01 - 常见 Bug 原因分析

常见 Bug 诱因的分类与防范方法总结。

常见 Bug 诱因

中文编码

全角符号误用为半角（如中文分号 ； 代替英文 ;）。编辑器一般能识别并报错，根据报错定位修改即可。项目文件名含中文字符也可能导致乱码。

数据中的全角字符：全角/半角差异不止出现在代码中，还可能藏在数据库存储的数据里，肉眼完全不可辨。案例：搜索助手名称「软件开发人员」查不到结果，搜「软件开发」却能搜到；用 id 查库确认数据存在，把库中值复制出来当条件又能查到——两个「一模一样」的 SQL 一个有结果一个没结果，最后 MD5 比对发现哈希不同，逐字对比才定位到「人」字是全角。排查思路：① 前端确认请求参数 → ② 开启后端 SQL 日志确认查询语句 → ③ 把 SQL 拿到数据库控制台直接执行 → ④ 复制库中存储值作为条件比对 → ⑤ 仍不一致则用 MD5/字节级对比确认字符串差异。教训：看到的不一定是真实的，肉眼相同 ≠ 字符串相同。

容器缺中文环境导致缓存 key 碰撞：编码问题也可能出在「环境层」而非数据本身。案例：数据可视化系统按不同筛选条件（一班/二班）查询成绩，结果却总是一班的。逐层排查——前端请求参数正确、SQL 已拼接 where 班级条件、数据库客户端直查结果不同，说明数据本身没问题；最终看线上日志发现 SQL 里的中文全部变成 ????（Docker 容器缺少中文 locale 导致乱码），而系统缓存 key 正是由 SQL + 条件计算生成的（key = 计算(sql, 条件)），中文变问号后「一班」「二班」两条 SQL 算出同一个 key，第二次查询直接命中了第一次的缓存。修复：容器配置补充中文环境支持后重新构建。教训：① 本地执行同一函数 key 不同、线上却相同——逻辑没问题时要怀疑运行环境差异；② 乱码不只是显示问题，参与逻辑运算的字符串（缓存 key、拼接参数）被环境编码破坏会产生隐蔽的脏数据。排查时先看日志等「证据」，再怀疑代码逻辑。

代码不规范

变量命名随意导致代码难以理解和维护。拼写错误的变量名不敢全局修改，容易遗漏。建议遵循团队命名规范。

复制粘贴

粘贴代码后漏修改变量名或注释，导致项目中存在多处冗余变量。每次粘贴后仔细核对修改点。

硬编码

常量（IP 地址、URL、阈值等）直接写死在代码中。修改时需逐文件查找替换，易遗漏。建议统一抽取为常量或配置项。

未释放资源

数据库连接、HTTP 连接、文件 I/O 流等资源使用后未释放，导致连接池占满。不影响功能可用性，但压测才能发现。建议使用 try-with-resources 或 finally 块确保释放。

圈复杂度过高

if/else 分支过多、嵌套过深导致代码难以维护和修改。建议：

  • 写复杂逻辑前先画流程图
  • 多用注释
  • 通过抽象、封装、设计模式降低复杂度

依赖冲突

项目同时引入多个依赖时，不同依赖可能要求同一类库的不同版本，导致启动失败或运行时异常。建议合理管理依赖版本，使用 Maven/Gradle 的依赖仲裁机制。

依赖版本漂移（lock 文件未提交）：Node 项目的 yarn.lock / package-lock.json 没提交到仓库，团队成员各自 install 时拉到的依赖版本不同。案例：一人为了装通依赖升级了某个包的版本，结果升级后该组件的函数参数变了，旧代码取 e.props.searchValue 得到 undefined（类似 Java NPE）；随手加可选链 e?.props?.searchValue 后报错消失、代码顺利合并，但该行逻辑其实已经失效——直到某天功能真用不了才排查出来。教训：① 报错消失 ≠ Bug 修复，判空/可选链只是掩盖了「数据路径已断」的事实，要追问为什么之前不报错、现在报错（别人没改代码，那变的一定是第三方依赖）；② 能不升版本就别升，代码能运行就别动；③ 升级依赖后必须做充分测试，代码能跑不代表功能可用。

不区分环境

开发环境与线上环境混用，导致测试数据污染线上数据库。建议严格分离开发/测试/生产环境。

不做自测

不写单元测试，修改代码后以前正常的功能突然报错。越晚发现问题修改成本越高。建议关键逻辑编写单元测试。

不做评估

不评估系统并发量、数据量级、接口时延，随意选择技术栈。建议上线前进行压力测试和容量评估。

自作主张

修改接口返回值或响应时长，影响下游依赖方。评估改动对上下游的影响，及时通知相关负责人。

文档读不全

只看到需要的函数就复制使用，忽略文档中的注意事项和边界条件。建议完整阅读相关文档章节。

版本号错误

未注意技术文档的版本号，使用被淘汰或尚不支持的语法。建议选择与项目引入版本一致的文档。

不了解需求

不明确需求就写代码，代码无 Bug 但不符合用户预期。写代码前先确认「做什么」和「为什么做」。

不做设计

不写方案直接写代码，容易遗漏关键点，后期推倒重来。复杂业务建议先设计再编码。
