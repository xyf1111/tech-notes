概念 14 - 硬编码的危害与避免

硬编码（Hardcode）的常见形式、真实事故案例与三种规避方案。

什么是硬编码

hardcode（硬编码）：把未来可能发生变化的信息直接以固定变量的形式写在代码中，或者把一段特殊逻辑写死。会导致日后修改和维护代码变得困难。

常见硬编码形式

  1. 写死 IP 地址和数据库账号密码

看似没什么问题，但接口地址一旦变更而业务负责人未收到通知或未及时修改，会导致所有请求失败。

  1. 写死业务逻辑（如查询火车票价格时对特定大客户返回促销票价）：

这里其实有两个 hardcode：“10001” 和 “50”。后续该用户特殊身份失效、票价变化、或要给一批新 uid 添加特权，都需要改动代码、重新上线（大公司代码发布通常要过审批流程），非常麻烦。

真实事故：一行 hardcode 引发的加班

  • 背景：公司内部消息队列服务，项目使用生产者代理（由代理将消息推送到不同生产端，实现负载均衡）。代码中写死了代理的固定 IP：

  • 变故：消息队列服务团队公告 IP 即将变更，只能手动处理，操作流程：

    1. 代码中把 IP 改为指定的域名
    2. 用脚本检测线上机器到该域名的网络连通性（避免 ping 不通）
    3. 部署到测试环境，进行消息推送测试
    4. 测试通过后提交代码，等审批
    5. 审批后灰度部署（只升级部分机器）
    6. 观察无问题，全量部署

  • 深藏不露的坑：所有使用该消息队列的代码都配的固定 IP。通过 gradle build --scan 扫描项目依赖的 jar 包排查，发现一个用于监控数据上报的 jar 包中也写死了同一 IP → 将 IP 切换为域名后升级 jar 包版本。

  • 连锁反应：使用该 jar 包的项目非常多，不升级的话到期都会受影响 → 调查所有可能使用该 jar 包的团队，逐一发送升级通知。

  • 教训：一行 hardcode 就能带来巨大的风险和工作量；藏在依赖 jar 包里的 hardcode 最隐蔽、影响面最大。

如何避免硬编码

1. 变量引用（常量抽取）

为相同的固定值定义变量（常量），最好放在单独的类或文件中，修改时只改一处：

调用第三方接口时，最好不要直接写死 IP，而是用域名作为地址调用，通过在机器上配置 host 来改变实际服务 IP，便于维护。

2. 配置化

把所有可能改动的信息（数据库账号、密码、服务端口等）单独存放到配置文件中管理，通过读取配置获取信息。修改时只需改配置文件，不用动代码——目前项目开发中最常用的一种方式。

3. 动态配置（配置中心）

配置化仍有一个问题：改动配置后项目可能需要重启才能生效，不够灵活。为此可利用分布式配置中心实现动态配置：将配置存放在数据库或分布式缓存、Etcd 中，业务代码引入 SDK 监听配置变量；配置修改时变量值同步更新，无需重启项目。

主流配置中心：携程 Apollo、阿里 Nacos、Spring Cloud Config。多数提供可视化界面，方便配置管理、修改发布和版本控制。
