概念 20 - SDK 设计与编写经验

SDK（软件开发工具包）是帮助开发软件的工具集合（代码 + 文档 + 示例），优秀的 SDK 应具备易用、可理解、可扩展、高效稳定四个特征；把通用功能（如文件上传）封装成 SDK 供各系统复用，可避免重复造轮子、统一实现差异、大幅提升开发效率。

核心要点

什么是 SDK

  • 定义：SDK（Software Development Kit）= 软件开发工具包，是帮助我们开发软件的工具集合，除代码外一般还搭配文档、示例。
  • 引入方式：SDK 需要引入到项目中才能使用，如 Java 的 JDK 需通过 import java.util.* 语法引入；多数 SDK 需人工或通过项目管理工具将文件下载到指定路径。
  • 使用好处：
    • 避免重复开发：公司多个系统都要实现文件上传（分块、断点续传、秒传、文件存储、文件管理等），只需一个团队编写一套通用 SDK，其他系统引用即可，大大减少工作量、提高开发效率；
    • 统一实现差异：同一个功能不同人实现效率差异巨大（有人运行 1 秒、有人运行 1 小时），共用 SDK 能减少各项目在相同功能上的差异；
    • 每个系统各自开发同样的功能就是「重复造轮子」，在大多数情况下不是明智之举。

优秀 SDK 的四个特征

简单易用、通俗易懂（可理解）、便于扩展、高效稳定。用户选型时倾向于几行代码就能用起来的 SDK，而不是读完长文档再写几十行代码才能生效。

易用性三招

统一调用

良好命名

  • 函数命名符合用户习惯：解析功能叫 parseXXX、判空叫 isEmpty，让用户不看文档、只看函数名和参数就能猜出用途；
  • 多使用、多参考别人的 SDK，养成习惯后会发现大家起名都差不多；
  • 尽量让 SDK 中的类名（函数名）不与别人的完全一致，否则用户面对一堆同名函数会困惑该用哪个。

可理解性四招

结构清晰

按功能或类别分包、分层整理代码，让人一眼看出各目录的职责。如经典 Java 项目结构：service 放业务逻辑、constant 放常量、utils 放工具类。

统一风格

目标是让项目看起来是同一个人写的：缩进统一（如 4 个空格）、命名统一（如驼峰式）；功能相似的代码命名与用法必须统一，不要一会儿叫 parseXXX、一会儿叫 jiexiXXX。团队开发难以天然做到这点，需要一套通用代码规范来保证。参见 概念 15。

编写注释

给每个类和函数的开头都加上注释，包括功能描述、参数含义、返回值含义等，让用户不看文档、只看注释就能知道它是干嘛的、怎么用。

说明文档

编写用户手册：如何引入 SDK、有哪些功能、应该怎么使用，可补充关键实现细节和常见问题列表。没有文档的 SDK，用户一般不会选用。

可扩展性两招

轻量依赖

尽量减少 SDK 对其他类库的依赖：一个几十 KB 的轻小工具类，没必要再引入几百 KB 的依赖库。轻量依赖不仅能减小 SDK 体积，更能减少依赖冲突的可能性——引入一个工具类后整个项目跑不起来的情况并不少见。

自定义实现

高效稳定三招

测试

  • 编写单元测试（UT），最大程度覆盖 SDK 的功能和代码；
  • 每次改动代码后、发布新版本之前，都要完整执行一遍测试，不要盲目自信；
  • 通过压力测试估算执行效率（如每秒最多同时执行 3 次、每次 500 毫秒），将这些信息补充进说明文档给用户预期；也可通过压测优化性能。

兼容性

  • 重要的函数和接口尽量减少改动，尤其是函数名、入参和返回值；
  • 大改动时新写一个函数，给老函数打上 @Deprecated 标注表示已过时，引导用户迁移（如不要突然把 isValid(String) 改成 checkValid(StringBuilder)，否则用户升级时一脸懵逼）；
  • 版本号语义：小改动只改小版本号（0.0.1 → 0.0.2），大改动才改大版本号（1.0 → 2.0），给用户「这次改动可能不兼容」的预期。

暴露异常

  • 让调用方感知 SDK 代码中可能抛出的异常，交给他们做相应处理，防止意料之外的错误；
  • 合理打印日志，尤其是异常日志，出问题时让调用者知道出了什么问题，便于排查。

结尾建议

建议学编程的同学多自己动手写 SDK，并按照易用、可理解、可扩展、高效稳定这几个维度去优化它，对提升编程能力很有帮助。
