Java 56 - OOM 内存溢出排查实战

线上 Java 服务 OOM（Out Of Memory）的完整排查套路：看日志 → dump 堆内存 → MAT 分析 → 定位大对象 → 调参救急 + 根治。本文是 BI 数据分析平台真实事故复盘。

事故现象

某天系统突然崩了、用户看不到内容，查日志发现 Java 后台程序发生 OOM（内存溢出）。

排查流程（套路）

  1. 先恢复、后排查：把部分容器重启恢复服务，留一台用于分析——线上事故优先止损，别让用户一直等。
  2. 看日志：能见到 OOM 相关报错，以及大概哪个线程、哪段代码触发（但代码本身可能看不出问题——OOM 往往是数据量/内存问题，不是代码逻辑问题）。
  3. dump 堆内存：用 jmap 等工具导出堆快照。内存大时 dump 很慢（本案例等 40 多分钟、每份 2-3G），建议 dump 两份不同状态便于对比分析。
  4. 分析 dump 文件：用 JVisual VM 或 MAT（Memory Analyzer Tool） 打开，看哪些对象占内存、有没有大对象没被回收。
  5. 看 GC 状态：上容器查 GC 日志/命令，确认 Full GC 是否触发过。

真相：大对象一次性撑爆堆内存

本案例分析结果：内存几乎全被一个 List 占用——100 万条记录直接占 1.6GB。但这些对象都是 GC root Unreachable（可回收）的，也触发过 Full GC，为什么还是 OOM？

关键在 JVM 内存结构：

  • JVM 最大堆内存默认是系统物理内存的 1/4（容器申请 8G → 默认堆只有 2G）
  • 堆分代回收：新生代一般占堆的 1/3，老年代占 2/3
  • 当一个大对象（超过新生代容量）要加载：新生代装不下 → 直接塞老年代 → 老年代也装不下 → 先触发一次 Full GC → Full GC 后仍装不下 → OOM

比喻：大家慢慢丢垃圾、工人定期来清空，垃圾箱不会爆；但一个巨大的垃圾直接跳进垃圾箱，装不下就爆了。

紧急处理：调整 JVM 最大堆参数 -Xmx8192m 增大堆内存（可用 jmap 查看当前堆参数；JDK 9+ 命令有变化、新增了 jhsdb，用到时现查即可）。但这只解决燃眉之急，必须找到一次性占 1.6G 的数据是什么。

根本原因：HashMap 存海量行的内存膨胀

List 里装的全是 Map，每个 Map 表示数据库一行，共 100 万行 × 15 列。这些数据在数据库/Excel 里不到 100MB，转成 Java 对象却膨胀了十几倍——实测 105 行 × 10 列就占 155.9KB，100 万行就是 1.6G。

为什么 HashMap 这么占内存：每个 HashMap 对象包含 12 字节 Java 对象头 + 4 个引用字段 + 3 个 int 字段 + 1 个 float 字段 = 44 字节；JVM 要求对象大小是 8 字节的倍数，再补 4 字节对齐——一个空 HashMap 就占 48 字节，用它逐行存数据远比文件格式占空间。

改进方案：海量行数据不要用 HashMap（对象开销太大），改用 List + 下标表示一行数据，内存占用大幅下降。

经验教训

  • 申请容器资源时要评估数据量级与对象的内存膨胀系数（文件 100MB ≠ 内存 100MB），别按文件大小估内存
  • OOM 排查先看日志定位触发点，再 dump + MAT 找占用大头，最后区分「可回收对象多但装不下大对象」与「内存泄漏」两类情况
  • 八股文里的 JVM 分代回收、HashMap 结构，背过不如踩过一次坑记得牢——实践 + 翻车是印象最深的老师
