Java 07 - 并发三大根源：可见性、原子性、有序性

并发问题的三大根源：CPU 缓存导致可见性问题、线程切换导致原子性问题、编译优化导致有序性问题。

背景：并发问题从何而来

CPU 运算速度远大于 IO 速度，任务等待 IO 时 CPU 无法工作。为提高 CPU 利用率，进程中诞生了线程、CPU 添加了高速缓存、编译程序优化指令执行次序，以更合理地利用缓存——但随之而来的就是大量的并发问题。

1. CPU 缓存导致的可见性问题

  • 单核 CPU 时代：所有线程在同一 CPU 上执行，缓存与内存之间的数据一致性容易解决，一个线程对共享变量的修改，另一个线程能立刻看到——这种特性称为可见性。
  • 多核 CPU 时代：每个 CPU 都有自己独立的缓存，多个线程在不同 CPU 上执行时，会把内存中的变量复制到各自 CPU 缓存中，处理完再写回内存，线程之间的可见性无法保障。

验证示例：双线程各加 10000

直觉上结果应为 20000，但实际运行时每次输出都小于 20000。原因：两个线程同时执行时，都把 sum = 0 加载到自己的 CPU 缓存中，各自执行 sum++ 后缓存中的值都是 1，写回内存时结果不是期望的 2，而是 1。

2. 线程切换导致的原子性问题

线程通过获取 CPU 时间片来调度：拿到时间片的线程处于执行状态，没拿到的处于就绪状态，等待系统分配下一个时间片。

两种调度模型

  1. 分时调度模型：系统平均分配 CPU 时间片，所有线程轮流获取。
  2. 抢占式调度模型：系统按线程优先级分配时间片，优先级高的优先分配；若所有就绪线程优先级相同则随机选择，优先级高的线程获得的时间片相对更多。

Java 的线程调度模型采用抢占式调度。

sum++ 并非一步完成

高级语言都需要编译成 CPU 指令才能执行。sum++ 这一行编译后至少包含三条指令：

  1. 将 sum 变量从内存加载到 CPU 寄存器
  2. 在寄存器中执行 +1 操作
  3. 将 sum 变量写回缓存

当执行第 1 步时，线程的时间片耗尽发生线程切换，最终结果就是 1 而不是 2。任务切换可能发生在任意一步。

原子性：一个或多个操作在 CPU 执行的过程中不被中断的特性。代码看似一行，实际被拆成多条 CPU 指令，编程时需要注意代码层面的原子性。

3. 编译优化导致的有序性问题

CPU 在执行指令时会调整指令执行顺序以提升效率。指令顺序优化可能发生在编译、CPU 指令执行、缓存优化几个阶段，优化原则是：只要保证重排序后不影响单线程的运行结果，就允许指令重排序发生。

new 对象的三步非原子操作

一个对象的 new 操作也不是原子性的，分为三步：

  1. 给对象分配内存
  2. 在这块内存上初始化对象
  3. 将这块内存地址赋值给变量

不正确的双重检查锁单例

假设 A、B 两个线程同时调用 getInstance，同时发现 instance == null。由于指令优化，正常 123 的顺序可能变成 132：先分配内存并赋值引用，再初始化对象。此时另一个线程看到非 null 的 instance，拿到的却是一个尚未初始化完成的对象，使用时就可能发生空指针异常。

解决方案：为 instance 变量添加 volatile 关键字（IDEA 也会给出提示），禁止指令重排序。

总结

volatile 解决可见性与有序性问题，synchronized / Lock 解决原子性问题（后续文章再详细介绍 Java 如何解决这三大问题）。
